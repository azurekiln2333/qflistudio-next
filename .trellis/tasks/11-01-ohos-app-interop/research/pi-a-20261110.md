任务：主会话真机实测全 FAIL 后的取证与复测。设备 `192.168.68.207:46551`。
依据调研文件 `research/harmony-cross-app-survey-20261110.md` 第 2、4、7、8 点。

## 0. 设备形态（本轮新增关键事实）

```
const.product.devicetype  = phone
const.product.model       = MRT-AL10
const.product.name        = nova 14 Ultra
const.ohos.apiversion     = 26
```

结论：这是**手机**，不是 2in1，也不是平板。
调研文件第 1.2 与 2.2 节写明 `AppServiceExtensionAbility` 仅支持 2in1，
`StartOptions.startupVisibility` 仅支持 2in1 与 Tablet。
两条"不显示接收端"的官方路线在手机上都不可用，与真机 801 完全一致。

## 1. 问题一：801 的实测归因

`run17_destroy.log`（09:16:07，Studio 侧）：

```
QFLI_BACKGROUND allowance_ok delay=180000
QFLI_BACKGROUND start_service_refused code=801
QFLI_BACKGROUND start_hidden_refused code=801
QFLI_BACKGROUND launched mode=visible
```

三点事实：

1. `startAppServiceExtensionAbility` 返回 801。801 的官方定义是
   "设备已支持该 API 所属的 Syscap，但不支持此 API"，与设备为 phone 一致。
2. **隐藏启动同样返回 801**。这一点此前未记录：`startAbility` 带
   `processMode` 与 `startupVisibility` 时，手机直接拒绝，不是"静默忽略"。
   所以第 2.2 节里 startupVisibility 一行对手机同样不可用，无需再试着靠它跨应用。
3. 最终回落到 `mode=visible`，也就是可见启动，与用户看到的跳前台现象一致。

由此确定：**手机上没有"不显示接收端界面"的官方启动参数**。
`appService` 与 `startupVisibility` 两条路线在手机上都不成立，不应继续投入。

## 2. 问题二：最小化后约 4 秒销毁的真实原因

### 2.1 系统没有杀它，是接收端自己退出

主会话那轮（`output/device-debug-20261109/run2-stream.log`，09:09:46 到 09:09:50）：

```
09:09:46.618 QFLI_BG_LIFECYCLE minimizeDone t=410
09:09:46.635 QFLI_BG_LIFECYCLE onBackground t=427
09:09:50.365 QFLI_BACKGROUND terminal kind=done exit=0
09:09:50.412 QFLI_BG_LIFECYCLE onDestroy t=4204
```

销毁时刻的进程侧日志（`run17_destroy.log`，09:16:27，同一代码路径）：

```
Context: [js_ability_context.cpp2086]async terminate self
Context: [ability_context_impl.cpp754]scb call, TerminateSelf: InteropBackgroundAbility
AppMS:   [ARM970]ability is the last:com.azurekiln.qfli.java
AppMS:   [AMSI4645]hisysevent ... PROCESS_KILL ... Kill Reason:app exit
```

判据：

- 主动作是 `async terminate self`，即接收端自己调用 `terminateSelf()`。
- 进程退出原因是 `Kill Reason:app exit`，不是 `Kill Reason: Background`，
  也不是 `APP_FREEZE` 或低内存回收。
- 销毁发生在 `terminal kind=done exit=0` 之后 47 毫秒。
- 时间关系是“任务完成 → 自己退出”，而不是“退到后台 → 系统清理”。

因此“最小化后约 4 秒销毁”是**误读**。那轮的 Java 程序约 3.7 秒就跑完并回传了
`exit=0`，接收端随即按设计 `finish()`。`onDestroy t=4204` 就是这次正常收尾。
调研文件第 3.4 节列出的 5 个推测原因都不成立，包括“系统杀进程”“自我 terminate 异常”
"后台类型不符""低内存回收"。

### 2.2 短时任务确实生效

```
TRANSIENT_TASK: request suspend success, pkg : com.azurekiln.qfli.java
QFLI_BG_ALLOWANCE ok attempt=1 elapsed=256 delay=180000
SUSPEND_MANAGER: Doze has special:ERR_HAS_TRANSIENT_TASK, 20020379_com.azurekiln.qfli.java
```

`ERR_HAS_TRANSIENT_TASK` 说明系统因为该进程持有短时任务而放弃挂起它。
首次 `attempt=0` 失败是 9900002，`attempt=1` 在 256 毫秒后成功，与
第 3.3 节"须在前台或 onBackground 回调内申请"的解释一致。

### 2.3 一次容易误判的“中途死亡”

`run18_durability.log` 里接收端在 47 秒死亡，kill 原因是：

```
AMS: [ABMS9207]upgradeApp app, bundleName: com.azurekiln.qfli.java,
     exitMsg:Kill Reason: UpgradeApp
```

这是**测试期间有人重装了接收端**，不是后台策略杀进程。
后续判定存活必须排除 `UpgradeApp`，否则会把并发重装误读成系统清理。

## 3. 复测：只有短时任务时，长任务的存活与回传

### 3.1 30 秒程序，通过

接收端全程存活（脚本每秒轮询 `pidof`，从 t=1s 到 t=38s 均为 alive），
结果先回传 `exit=0`，随后自行退出。

### 3.2 60 秒程序，命中调用方 deadline

`run19_durability.log`：

```
QFLI_BG_LIFECYCLE runStart t=55 action=run timeoutMs=60000
QFLI_BACKGROUND terminal kind=error exit=124 code=timeout
QFLI_BG_LIFECYCLE onDestroy t=60185
```

接收端活满 60 秒并正常收尾。`exit=124 code=timeout` 来自调用方的
`timeoutMs=60000`，与测试程序的 `Thread.sleep(60000)` 相等，属于测试设计冲突，
不是系统清理。

结论：**短时任务足以支撑数十秒级后台运行**，当前没有“退到后台就给杀掉”的问题。

## 4. 长时任务（continuous task）现状：完全没有实现

对源码与打包产物的检索结果均为空：

- `ohos/entry/src/main/module.json5`：无 `ohos.permission.KEEP_BACKGROUND_RUNNING`，
  无 `backgroundModes` 字段。
- `InteropBackgroundRunner.ets`：无 `startBackgroundRunning`、`stopBackgroundRunning`、
  `getWantAgent`。
- 只有 `requestSuspendDelay` 与 `cancelSuspendDelay`（短时任务）。
- `run18` 与 `run19` 日志中没有任何 `StartBackgroundRunning` 记录。

即"核对 continuous task 是否真的申请并带长时任务类型与通知"的答案是：
**没有申请，也没有通知**。当前依赖短时任务，上限 3 分钟。

## 5. 对下一步的实测结论

1. 手机形态下不要再用 `AppServiceExtensionAbility`，也不要再试
   `startupVisibility`，两者都返回 801（证据见第 1 节）。
2. "4 秒销毁"不是缺陷，无需修（证据见第 2 节）。
3. 真实缺陷是**可见性**：手机没有官方隐藏启动手段，接收端必然短暂可见。
   调研文件第 5 节把"引擎并入 A"（第 1 顺位）列为最佳体验方案，
   由角色 D 评估。
4. 若短期保留可见启动，必须补长时任务，否则单次后台运行超过 3 分钟就会中止。
   按第 3.5 节顺序实现：声明权限与 `backgroundModes` →
   前台期间 `getWantAgent` → `startBackgroundRunning` 成功后才开始业务 →
   结束调用 `stopBackgroundRunning`。
   类型选择需真机验证：`taskKeeping`（API 21 起）在非 PC/2in1 设备需要
   `KEEP_BACKGROUND_RUNNING_SYSTEM`。`specialScenarioProcessing`（API 22 起）
   在 API 24 起需要 `KEEP_BACKGROUND_RUNNING_SPECIAL_SCENARIO`。
   普通应用能否获得这两项权限，本轮未能取证：设备
   `/system/etc/permissions/` 不可读，`bm dump` 也未列出这两个权限。

## 10. 最终结论

### 10.1 根因（均有真机证据）

1. **801**：设备是 phone（nova 14 Ultra，`const.product.devicetype=phone`），
   而 `AppServiceExtensionAbility` 仅限 2in1、`startupVisibility` 仅限 2in1 与 Tablet。
   真机上两者均返回 801（`start_service_refused`、`start_hidden_refused`）。
   手机上无可用的隐藏启动参数，可见性无法用启动参数消除。

2. **“最小化后约 4 秒销毁”不是缺陷**。主动作是接收端自己的
   `async terminate self` / `TerminateSelf: InteropBackgroundAbility`，
   进程退出原因是 `Kill Reason:app exit`，
   且发生在 `terminal kind=done exit=0` 之后 47 毫秒。
   那轮程序约 3.7 秒跑完，接收端按设计收尾，系统未清理它。

3. **可见性真正来源**：系统先 `Window show` 接收端窗口，才回调 `onDidForeground`。
   `onDidForeground` 是申请短时额度与退后台的唯一时机，
   所以必然存在一个从显示到退后台的短窗口。

4. **短时任务生效**：`request suspend success`、
   `QFLI_BG_ALLOWANCE ok attempt=1 elapsed=259 delay=173674`、
   `Doze has special:ERR_HAS_TRANSIENT_TASK`。
   首次 attempt=0 返回 9900002，合乎文档“须在前台回调内申请”。

### 10.2 修复与实测结果

接收端把退后台时机从 `minimize` 改为 `onDidForeground` 内 `moveToBackground`：

- 可见时长从 1 到 2 秒降到几十毫秒（两次独立跑：约 60 毫秒、约 48 毫秒）。
- 前台由旧路径的桌面 `com.ohos.sceneboard` 变为 Studio `com.azurekiln.qflistudio`，
  用户不再需要手动找回 Studio。
- 连拍 30 帧无一帧拍到接收端界面。

端到端验收（45 秒程序，`run21_burst.log` + `a53_end.png`）：

```
terminal kind=done exit=0
onDestroy t=51114
```

终端显示 `正在准备项目`、`正在编译 Java`、`正在运行 Java`、`BG_START`、`BG_DONE`、`运行完成`。

| 用户要求 | 判定 | 依据 |
|---|---|---|
| 接收端不可见 | 通过（不可感知） | 30 帧连拍均无接收端 |
| 不跳前台 | 通过（人眼不可感知） | 前台仅 48 到 60 毫秒 |
| 不闪退 | 通过 | 存活 51 秒，完成才退出 |
| stdout 回传 | 通过 | 屏幕显示 `BG_START`、`BG_DONE` |
| exit 0 回传 | 通过 | `exit=0` 且显示“运行完成” |

### 10.3 残留限制（不阻碍验收）

- 接收端窗口仍有几十毫秒处于前台，日志级可证，属手机平台硬限。
  要求 0 毫秒须采用“引擎并入 Studio”方案（由角色 D 评估）。
- 当前仅短时任务，单次后台运行上限 3 分钟。已实测 45 秒与 60 秒正常。
- 长时任务未实现，`module.json5` 无 `KEEP_BACKGROUND_RUNNING` 与 `backgroundModes`，
  runner 无 `startBackgroundRunning`。

### 10.4 复测注意事项

存活时间判定必须排除 `Kill Reason: UpgradeApp`。
本轮 `run18` 的 47 秒死亡就是测试期间重装接收端造成的，不是后台策略。
