# 角色 A（设备）现场反馈复现记录 2026-11-09

## 现场反馈

点“后台运行”后，接收端 `com.azurekiln.qfli.java` 跳到前台，随后退回桌面。
期望：接收端不可见，后台执行，stdout 与 exit 0 回传 Studio。

## 结论先行

1. 接收端**没有崩溃**。日志里没有本轮 jscrash / cppcrash / appfreeze 记录。
   接收端进程结束方式为 `PROCESS_KILL ... Kill Reason:app exit`，是它自己
   `terminateSelf()` 的正常退出。用户看到的“闪退”是可见窗口消失后落到桌面。
2. 用户看到的界面是**系统启动页**，不是接收端的 idle 页。
   启动页由 module.json5 的 `startWindowIcon` 与 `startWindowBackground` 决定：
   - `startWindowIcon` = `$media:icon`
   - `startWindowBackground` = `#F8F9FF`（浅灰）
   接收端 idle 页是深色底 `#101014` 加文字「QFLIJVMX 正在处理跨应用请求」。
   抓到的那帧是浅灰底加 logo，与启动页吻合。
3. 根因：跨应用启动一个 UIAbility 时，系统必然进行场景转场并绘制启动页。
   当前所有“隐藏启动”手段都要求调用方与目标应用同 bundle 名，本项目做不到。

## 复现步骤（可重复）

1. 重装 Studio 与接收端，冷启 Studio。
2. 打开项目 `BackgroundSmoke`。
3. 点右上角 ⋮，选「后台运行（实验）」。
4. 1 秒内连拍截屏。

工具在本目录 `pi-a/tools/`：

- `ui.ps1`：按文本或按钮边界定位控件，避免硬编码坐标。
- `flash-burst.ps1`：启动运行并在设备侧连拍 30 帧。
- `foreground-test.ps1`：每秒记录前台 bundle 归属。
- `cancel-test.ps1`：点 Stop 验证取消。
- `complete-test.ps1`：前台保持时验证 stdout 与 exit 0。

## 证据一：接收端可见约 1 到 2 秒

`flash-burst.ps1` 在设备侧连拍，帧间隔 0.5 到 1.0 秒。
第 1、2 帧（248 KB、208 KB）是接收端启动页全屏，第 3 帧起是桌面（3.7 MB）。
截图保存于 `pi-a/burst/flash_1.png`、`pi-a/burst/flash_2.png`。

`foreground-test.ps1` 每秒采样前台 bundle，12 次采样全部为
`com.ohos.sceneboard`（桌面），说明运行结束后设备停在桌面，Studio 不在前台。

## 证据二：系统做了完整场景转场

`run13_foreground.log`、`run14_burst.log`：

```
SCBMain: startSceneTransition:{...bundleInfo:InteropBackgroundAbility/com.azurekiln.qfli.java...}
WMS:   SCBScenePersistent --> PersistentId=7670 not support hidden status.
WMS:   setTranslateXWithDfx from 0 to 363.42857142857144
SYS_UI: QuickBackIconVm --> callback: from:com.azurekiln.qflistudio to:com.azurekiln.qfli.java
```

`WMSDecor: UpdateDecorEnable: decorVisible:1` 表明接收端窗口带装饰并可见。

## 证据三：请求中的隐藏启动被系统丢弃

`StartReceiver` 已传 `startupVisibility: STARTUP_HIDE`、`processMode` 与
`hideStartWindow: true`。系统在 AMS 侧记录的实际标志位是：

```
AMS: [AMC474]scb call, StartUIAbilityBySCB target: com.azurekiln.qfli.java/InteropBackgroundAbility, flags: 1
```

`flags: 1` 只含基础位，不含任何隐藏启动标志。隐藏启动没有生效。

## 证据四：SDK 文档写明跨应用做不到

SDK 23 `@ohos.app.ability.contextConstant.d.ts` 中，`ProcessMode` 的每个枚举值均写明：

> When using this mode, the target ability needs to have the same bundle name as the caller.

`@ohos.app.ability.StartOptions.d.ts` 同时写明：

> The properties processMode and startupVisibility must be set simultaneously.

因此 `startupVisibility` 的生效前提是同 bundle 名。接收端是另一个应用，
`processMode` 与 `startupVisibility` 必然无效。

`hideStartWindow` 的注释为：

> Hide start window or not when launch ability from same bundle.

同样是同 bundle 才能生效。

## 证据五：SDK 23 没有隐藏窗口的 API

`@ohos.window.d.ts` 里可用的窗口控制只有：

```
minimize(): Promise<void>
setWindowDecorVisible(isVisible: boolean): void
setWindowTouchable(isTouchable: boolean): Promise<void>
setWindowBackgroundColor(color: string | ColorMetrics): void
```

没有 `setWindowVisibility`，也没有 `WindowVisibility` 枚举。
接收端目前只能先进入可见状态，再在 `onDidForeground` 之后调用 `minimize()`。
`QFLI_BG_LIFECYCLE minimizeBefore t=420` 与 `minimizeDone t=421` 说明最小化发生在
启动后约 0.42 秒，此时启动页已经画出来了。

## 修复方向

隐藏启动在同 bundle 前提下才能生效，UIAbility 路径无法做到无感。
可选方向按代价排序：

1. 接收端改用 `AppServiceExtensionAbility`（API 20，无窗口），
   调用方用 `UIAbilityContext.startAppServiceExtensionAbility(want)` 启动。
   这是唯一不带窗口的跨应用后台能力。
2. 保持 UIAbility，但把启动页做成透明：`startWindowBackground` 的 alpha 设为 0。
   启动页仍会占据前台约 0.4 秒，只是不可见，且系统转场动画仍在。
3. 保留现状，明确告知这是平台限制。

## 待真机验证的风险

`startAppServiceExtensionAbility` 的文档错误码含
`16000200 - The caller is not in the appIdentifierAllowList of the target application`。
接收端的 extension 声明**没有** `appIdentifierAllowList`。
SDK 23 的 `modulecheck/module.json` 将其定义为
「List of applications that are allowed to launch this ExtensionAbility」，非必填。

因此存在两种可能，必须真机区分：

- 未声明即允许同设备应用启动：无感路径直接生效。
- 未声明则只允许同应用启动：Studio 收到 16000200，回退到可见路径。
  此时需要接收端在该扩展上声明 Studio 的 appIdentifier。

调用方身份校验能否在扩展路径生效：

接收端的 `allowed()` 依赖 want 参数 `ohos.aafwk.param.callerBundleName`。
SDK 23 `@ohos.app.ability.Want.d.ts` 写明该键的取值：

> The values of the following keys are assigned by the system. Manual settings do not take effect,
> since the system automatically changes the values to the actual values during data transfer.
> - ohos.aafwk.param.callerBundleName: bundle name of the caller.

因此该参数由系统注入并覆盖，不是调用方可伪造的值。
旧的 UIAbility 路径已验证该参数正常注入（日志出现 `runStart`，说明 `allowed()` 通过）。
扩展路径是否同样注入，仍需真机日志确认；若未注入，服务会输出
`QFLI_BG_SERVICE caller_not_allowed caller=` 并回传 `caller_not_allowed`，
不会静默失败。

## 最终结论

根因：接收端原来用 `UIAbility` 承载后台运行。跨应用启动 `UIAbility` 时，
系统必然建立场景并播放转场，先绘制该 ability 的启动页。
三个隐藏启动手段都要求调用方与目标应用同 bundle 名，无法跨应用生效：

- `StartOptions.startupVisibility` 必须与 `processMode` 同时设置。
- SDK 23 `contextConstant.d.ts` 对每个 `ProcessMode` 值都写明
  “the target ability needs to have the same bundle name as the caller”。
- `StartOptions.hideStartWindow` 注明 “when launch ability from same bundle”。

系统侧日志同时证明隐藏启动没被受理：
`StartUIAbilityBySCB ... flags: 1`，不含任何隐藏启动标志位。
故接收端只能先可见、再 `minimize()`，最小化后前台回到桌面，用户看到「跳前台后闪退」。
所谓“闪退”不是崩溃：进程退出为 `Kill Reason:app exit`，本轮无任何 jscrash / cppcrash / appfreeze。

修复：改用无窗口的 `AppServiceExtensionAbility`。

- 接收端：`ohos/entry/src/main/module.json5` 声明 `InteropBackgroundService`
  （`type: appService`，无 startWindow），
  实现文件 `ohos/entry/src/main/ets/interop/InteropBackgroundService.ets`。
- 调用方：`ohos/entry/src/main/ets/interop/StudioBackgroundInterop.ets`
  改为 `context.startAppServiceExtensionAbility(service)`，失败时无损回退到旧路径。
- 共享执行器：`InteropBackgroundRunner.ets` 对无窗口宿主把额度拒绝降级为自身 deadline。

已验证：两侧构建成功，两个 HAP 安装成功；
打包产物中该扩展为 `type=appService`、`exported=true`、无 startWindow 字段；
Studio 包内同时存在 `startAppServiceExtensionAbility` 与旧的 `InteropBackgroundAbility`；
设备侧 `bm dump` 已列出 `extensionTypeName: appService` 与独立进程 `com.azurekiln.qfli.java:appService`。

未验证：接收端不可见、不跳前台、stdout 与 exit 0 回传的真实端到端结果。
阻塞原因是设备已自动锁屏，`aa start` 报 `10106102`，连无窗口扩展也无法启动。
按硬性规则不得绕过锁屏或输入解锁凭据，因此本轮停在真机验证前一步。
解锁后按上文六个步骤完成验证即可闭环。
