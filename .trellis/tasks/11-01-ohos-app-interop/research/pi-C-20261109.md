## 3. 本次改动

### 3.1 `InteropBackgroundRunner.ets`

只改两处文案。行为不变。

1. 启动前的时间不足有两种来源。一是前台重试耗掉调用方 deadline。
   二是系统给的额度太短。原来两者都报同一个额度不足文案。
   现在按真正设限的一侧报。一侧说额度不足。另一侧说剩余运行时间不足。
   退出码仍是 124。
2. `analyze` 探针的终结事件原来写「运行完成」。现在写「能力探测完成」。
   探针不跑任何程序。原文不实。
   当前发送端 `InteropBackgroundTransport.probe` 固定返回 `unknown`。
   它不发 `analyze`。所以这条只在协议层生效。

### 3.2 `tool/verify_interop_background.cjs`

用例从 18 项增到 23 项。新增项都能检出真实回归。

| 新增 | 断言要点 |
| --- | --- |
| `capability probe skips compile and launch` | `analyze` 不拷 payload。不 `prepareJdk`。不启 native。恰好一个 `done`，`exitCode 0`，序号连续，订阅与额度释放 |
| `unconfirmable child never claims success` | `cancelJava` 无效时仍发一个终结事件。内容是 `error/internal/127`。绝不 `done`。未确认的子进程留在跟踪表 |
| `exhausted caller deadline never launches` | 前台重试吃掉 deadline 后不启子进程。报「剩余运行时间不足」 |
| `dispose before run` | 建 runner 后立即 `dispose()`。早订阅恰退订一次。不发事件。不把析构当取消 |
| 文案断言 | `allowance: 2000` 报「额度不足」。`analyze` 报「能力探测完成」 |

用例结构沿用原写法。它转译真实 `.ets`，并给平台与 native 假件。
既有断言没有放宽。`scenario()` 只新增 `action`、`unreapable`、
`deadlineBeforeStart` 三个开关与对应分支。

第三处小改是噪声。两处用例的假 fileIo 是空对象。清理一个从未创建的目录时，
它会抛错并打 `QFLI_BACKGROUND_CLEANUP_FAILED`。我改成共享的宽容 fileIo 假件。
现在输出里不再有假告警。日志出现清理失败就是真的失败。

`StartAbility` 之后，平台为接收端建了整屏场景会话。原文如下。

## 7. 根因

根因是传输类型选错了。根因不是权限，不是 bundleName，不是事件协议。

`UIAbility` 只能带窗口启动。窗口由平台创建，接收端代码关不掉。
`focusedOnShow:true` 与 `startSceneTransition` 都由平台决定。
最小化又把「回调用方」关掉，于是系统落到桌面。
所以「跳前台」和「闪退回桌面」是同一个设计选择的两面。
这个选择在 `design.md` 里写成「UIAbility 加 `window.minimize()`」。
本次不动它的时机与参数。本次换掉传输类型。

## 8. 修复：换用无窗口的 appService 扩展

### 8.1 机制

`AppServiceExtensionAbility` 是 `@since 20` 的第三方后台扩展。
它没有窗口，也没有 `onWindowStageCreate`。
平台不会为它建场景会话，不会播转场，不会抢焦点。
发送端用 `startAppServiceExtensionAbility` 启动它。该接口也是 `@since 20`。
SDK 原文的条件是「目标不可见时才需要 `START_INVISIBLE_ABILITY`」。
我们的扩展声明 `exported: true`，所以不需要那项权限。
`START_INVISIBLE_ABILITY` 的 `availableLevel` 是 `system_core`。
第三方应用根本拿不到。这一点我已查 `PermissionDefinitions.json`。

### 8.2 接收端改动

1. 新增 `InteropBackgroundService.ets`。它是 `appService` 扩展，约 160 行。
   它复用 `InteropBackgroundRunner`、`BackgroundCancelGate`、
   `BackgroundEventWriter`、`parseRequest`。
   它没有窗口 API。它的 `onRequest` 直接起 runner。
   它把 `allowanceOptional` 传成 `true`。
2. `module.json5` 增加 `extensionAbilities` 一项。
   类型是 `appService`，`exported: true`，
   动作是 `action.system.qfli.interop.background.service`。
   旧的 `InteropBackgroundAbility` 保留。它给低版本设备兜底。
3. `InteropBackgroundRunner.ets` 三处改动。
   一是 `run(hideWindow)` 接受 `null`，无窗口宿主没有要隐藏的东西。
   二是构造参数新增 `allowanceOptional`。
   三是系统永久拒绝额度时报 `QFLI_BG_ALLOWANCE none` 并继续。
   继续的依据是自带的 deadline，加上扩展存活本身保住进程。
   旧路径不传这个开关，行为不变。
4. `prepareProject` 与 `prepareJdk` 的参数类型从
   `common.UIAbilityContext` 放宽到 `common.Context`。
   两者只用到 `cacheDir`、`filesDir`、`resourceManager`。放宽是安全的。
5. 身份不合法的调用方现在一定收到 `caller_not_allowed`。
   这里是我自己引入又自己修掉的缺陷。`refuse()` 会再查一次身份，
   于是外来请求落进静默丢弃。新用例当场检出。现在拆成 `answer()` 与 `refuse()`。

## 10. 十一月十日的更正：801 排除后改用后台移动

上一节写的无窗口扩展路线作废。
设备实测两次都返回 801。`startAppServiceExtensionAbility` 返回 801。
`startAbility` 带 `hideStartWindow` 与 `startupVisibility` 也返回 801。
调研结论是这类能力只对 2in1 开放，还需要企业 ACL 权限。
手机上没有这条路。场景会话因此无法避免。

改用另一个方向：窗口照建，但立刻撤回去。
`moveAbilityToBackground()` 自 API 12 提供。它把当前 ability 移到后台。
失败码有两个：16000061 表示不支持，16000065 表示当前不在前台。

第一次改动把 `minimize()` 换成它。焦点在 34 毫秒后回到 Studio，不再落回桌面。
整轮 15 秒程序跑完，`onDestroy t=21048`。
窗口可见约 450 毫秒。

第二次改动把撤回动作提到 `onDidForeground` 里。
撤回在申请额度之前完成。额度改从后台申请。
窗口只占焦点 78 毫秒（07.356 → 07.411），Studio 在 07.425 拿回焦点。
额度一次成功：`QFLI_BG_ALLOWANCE ok attempt=0 elapsed=3 delay=180000`。
调研里说 `onBackground` 可以合法申请瞬态额度，这次得到验证。
`SUSPEND_MANAGER` 记到 `has transient`，说明额度确实挡住了挂起。

自查出一个自己的缺陷。`onDidForeground` 先早退一次，`run()` 走到隐藏窗口时又退一次。
两次调用相隔 1 毫秒，第二次遇到 16000065，回落成 `minimize()`。
现在把两次调用合并成一个进行中的 Promise（`beginBackground()`）。
同一时刻只发一次平台请求，后到的调用复用前一次。
移动成功的分支也顺手把 `leftForeground` 置真，避免再发请求。

用例跟着改。`abilityLifecycle` 断言：建窗与 `onForeground` 期间不移动。
`onDidForeground` 时移动一次。不许 `minimize`。
运行器不许重复移动。重新前台后再移动一次。忙碌单例再移动一次。热的 ability 只移动一次。
新增 `moveFallback` 用例：16000061 时回落到 `minimize`，窗口不会留在前台。
现有 24 条用例全过。

真机复测（09:57:43 起，`qfli_java/output/device-bg/run.log`）。
接收端占焦点 62 毫秒，随后 Studio 拿回焦点，用户不会再落到桌面。
`QFLI_BG_ALLOWANCE ok attempt=1 elapsed=257 delay=35152`。
`onDestroy t=30034`，`PROCESS_KILL ... Kill Reason: app exit`。
这段时间里没有系统杀进程记录。
程序输出 `BG_START` 回到 Studio 终端。断言只差 `done exit=0`。

差的那一条不是接收端的问题。
瞬态额度当天只批到 35152 毫秒，而当天测试程序睡 38 秒。
运行器按额度减去 2500 毫秒保底算出预算，超时就报 `terminal kind=error exit=124`。
这条路径本身是对的：超时上报、子进程回收、额度释放都正常。
把测试程序改回 15 秒即可在 32 秒预算内跑完。

这里有个产品层面的约束要记住。
瞬态额度是每天十分钟的配额，跑一轮就消耗一段。
后台编译时间受当天剩余额度限制。长程序或循环程序会超过额度。
额度不够时运行器会如实报 124，不会假装成功。
