### D5（P2，文档与实现不一致）API 20 下限只归给了 `onDidForeground`

`onDidForeground` 与 `commonEventManager.subscribeToEvent`（Promise 版）都是 `@since 20`
（`UIAbility.d.ts`、`@ohos.commonEventManager.d.ts:286`）。
`subscribeToEvent` 在本路由有三处调用：Studio 订阅结果、Java 的
`BackgroundCancelGate.arm`、runner 自身的取消订阅。B 的报告与 C 的
`tool/verify_interop_background.md` 都把 API 20 下限只归到 `onDidForeground`。

两个工程 `compatibleSdkVersion` 都是 `5.1.0(18)`，`targetSdkVersion` 分别是
`26.0.0` 与 `6.1.1(24)`。

- 本机（OS 7.0.0）有这几个符号，所以能跑。
- 装到 18/19 级设备上：`gate.arm()` 在 `onCreate` 就抛 `TypeError`（该调用在
  `try/catch` 内，只会少一个订阅），runner 的订阅抛出后归为 `internal`/127，
  Studio 侧 `start()` 直接失败。三条路径都不是 `Refusal`，文案无信息量。
- 处置：`design.md` 已按本次审查补上 §8a。代码侧需在三条 `subscribeToEvent` 前
  做一次能力判断，给出具名拒绝而不是抛错。

### D6（P2，本地码侵入协议闭集）Studio 侧新增了不在协议里的错误码

`StudioBackgroundInterop.start()` 会抛 `busy`、`notification_disabled`、
`notification_failed`，`cancel` 路径会抛 `cancel_failed`。它们以
`PlatformException` 形式到 Dart，`_fail()` 统一映射成 `transport_failure`/127。

- 行为可接受（都变成真实的 127），但这些码不在 `InteropErrorCode.all` 里，
  而 `design.md` §3.3 把错误码写成闭集。下一个实现者会以为 `busy` 是协议码。
- 处置：`design.md` §3.3 增加"客户端本地码，永不出现在接收端事件里"一行，
  或把 Studio 侧改成复用 `internal`。

### D7（P2，spec 与实现方向相反）认证与解析的先后

`interop.md` 要求"Authenticate session ID and token **before parsing** result content"。
Studio 的 `receive()` 是先 `JSON.parse(data.data)` 再比对 `sessionId`/`sessionToken`。
Dart 侧确实先认证再解析（它只看得到 map）。

- 实际风险很低（解析的是一段字符串，且有 16384 上限），但文档和代码已经不一致。
- 处置：改文档一行，或把 token 比对提到 `JSON.parse` 之前。后者做不到，
  因为 token 就在 JSON 里。所以应改文档措辞为"认证前不得依据事件内容做任何副作用"。

### D8（P2，边界竞态）首次通知授权弹窗吃满 10 秒启动预算

Dart `_invokeStart()` 用 `startupGrace`（默认 10 秒）等原生 `start` 回复，而原生
`start()` 在 `isNotificationEnabled()` 为假时 `await requestEnableNotification(context)`，
那是模态框，等用户点击。

- 首次安装后第一次后台运行，若用户犹豫超过 10 秒：Dart 先报
  "后台运行启动未在限定时间内确认"（127），原生随后仍会拉起接收端，
  由 `dispose`/`cancel` 收尾。
- 结论不是"数据错"，而是"用户看到的失败与真实原因不符"。
- 处置（属 B）：把通知授权从 `startupGrace` 的等待里拆出去，或在授权前先回一次
  `pending` 类回答。

## 1. 23:49 那一轮本已拷出 9900002 的证据

**结论（已证实）**：9900002 带该 message 时不是“额度耗尽”，也不是“后台停留过久”。

## 2. 结果帧丢失的根因（决定性证据）

那一轮的现象：Studio 只收到 3 帧，终态帧没到，19.8 s 后 JVMX 自己 `terminate self`，
退出码 0（`appspawn ... exit with code:0`）。

事件服务的投递日志给出了答案：

```
23:49:30.571 SUSPEND_MSG ... 20020380_com.azurekiln.qflistudio_44761, state:2      # Studio 进后台
23:49:31.816 SUSPEND_MANAGER ... DOZE_AFTER_ENTER_BG
23:49:33.832 SUSPEND_MANAGER ... Freeze pid: 44761 success.
             FROZEN_BY_START_WINDOW_AFTER_PULLED_FROZEN
23:49:34.963 Pid 48108 publish com.azurekiln.qfli.interop.background.EVENT to 100 end(1,0,0,1) freezePid[44761,]
23:49:35.277 ... freezePid[44761,]
23:49:50.284 ... freezePid[44761,]
23:49:50.343 ... freezePid[44761,]
```

对照 Dart 侧实际收到的三帧：`23:49:30.999 / 31.047 / 31.079`，全部早于 33.832 的冻结。

**根因（已证实）**：JVMX 从拉起那一刻就把前台从 Studio 手里拿走，`SUSPEND_MANAGER`
约 3 秒后冻结 Studio。冻结后 common event 一律以 `freezePid[44761,]` 拒绝投递。

## 3. 第 4 项评估：把引擎并入 qflistudio

### 3.1 先把“用 Worker 跑”这个前提纠掉

ArkTS 的 Worker 与 TaskPool 是 JS 隔离运行环境，跑不了 JVM。
当前引擎也不是一个可链接的库，而是一个**必须 fork 子进程**的 HotSpot：

- `cpp/jdk_process.cpp` 的做法是 `fork()`，子进程里 `dlopen` 四个库，
  再调 `JLI_Launch`，最后 `_exit(code)`。
- 子进程设 `PR_SET_PDEATHSIG(SIGKILL)`，stdout/stderr 重定向到文件。
- 没有任何 `-Xint`，`libjvm.so` 含 `CompileBroker`、`C2`、`TieredCompilation`。

所以正确的说法是“qflistudio 自己 fork 一个 JVM 子进程”，不是“Worker 里跑”。
这不影响可行性，但影响工作量与风险判断。

### 3.2 JIT 风险：结论是低，理由是现成的

同一份 `libjvm.so` 现在就在这个平板上运行，宿主也是
Flutter + ArkTS 进程。两个应用都是普通第三方签名 HAP。
系统看不到“这个 .so 属于哪个应用”的差异，只看到本应用 lib 目录里的库。
所以并入 qflistudio 不会新增“运行期代码拦截”的风险，
只会继承 qfli_java 已付的代价。

需要如实标注的不确定项：

- 本轮没有证据说明 C2 真的编译过。没有 `-Xint` 只说明“没禁”，
  不等于“编了”。要证实得在真机加 `-XX:+PrintCompilation` 看输出。
- 若目标机型的系统版本对可写且可运行的内存页有额外限制，两个应用会同时失效。
  这属于平台级风险，与合并方案无关。

判据（真机一行就能定）：

```
java -XX:+PrintCompilation -version   # 有编译行 = C2 在用
```

### 3.3 工作量的真实构成

要搬的东西（来自 `qfli_java` 实测）：

| 项 | 体积 | 来源 |
| --- | --- | --- |
| `jdk-arm64-v8a.zip` | 49.4 MB | `resources/rawfile/` |
| `.so` 集合 | 18.6 MB（40 个） | `ohos/entry/libs/arm64-v8a/` |
| 清单 `jdk-arm64-v8a.json` | 2.2 KB | 同上 |
| NAPI 模块 | 3 个 cpp，约 8.4 KB | `cpp/jdk_layout.cpp`、`jdk_process.cpp` |
| ArkTS 准备层 | `JavaBridge.ets` 5.0 KB | 解压、布局、方法通道 |
| Dart 准备层 | 354 行 | `mobile_jdk.dart`、`ohos_jdk_process.dart`、`mobile_jvm_launch.dart` |

qflistudio 侧现在是**零 native**：没有 `cpp/`，没有 `libs/`，没有 CMakeLists。
所以这不是搬文件，是给 qflistudio 第一次引入 native 构建链。

分四段做，每段都能单独验：

1. 加 native 构建链。
   `CMakeLists.txt` + `libace_napi.z.so`，把三个 cpp 编成一个模块。
   验收：`hvigorw assembleHap` 通过，模块能在 ArkTS 里 require 到。
2. 打包 JDK 资源。
   rawfile 放 49.4 MB zip 与清单，`libs/arm64-v8a` 放 40 个 `.so`。
   验收：HAP 体积从 172 MB 涨到约 240 MB，装机后 `filesDir/usr` 能解压。
3. 搬准备层。
   `JavaBridge.ets` 的 `prepare()` 基本可照搬，它只依赖
   `resourceManager` 与 `zlib`，没有跨应用逻辑。
   Dart 侧 354 行属于同一个 Flutter 平台，依赖只有 `dart:io`、`path`。
4. 接运行入口。
   编辑器现有的 run 入口改为调本地 `startJava`，
   不再走 `qfli_interop/background`。

相对工作量：第 1 段是本项目第一次引入 native，风险集中在这里。
第 2 段只是体积。第 3、4 段是搬运与接线，代码量小。

### 3.4 这个方案的代价，必须一并写清

- **HAP 从 172 MB 涨到约 240 MB。** 安装包翻近一半，下载与首次安装都变慢。
  两个应用都要装 JDK 的话，等于设备上存两份同样的 JDK。
- **重复维护。** JDK 升级要同时改两处，`qfli_java` 与 `qflistudio` 都会漂移。
- **qflistudio 从此带 native。** 构建链、ABI、崩溃隔离都要自己扛。
  目前它连一个 `.so` 都没有，这是结构性变化。
- **不再能跑其它语言。** 现在 `qfli_java` 是独立应用，Python 与 C 的路线
  仍可各自演进。合并只解决 Java 这一条。

### 3.5 建议

不把它当默认路线。理由是功能缺口已消失，
只剩 410 ms 的可见窗口，却要用近 70 MB 的包体与一条 native 构建链去换。

按收益排序：

1. 先接受 `mode=visible` 并把 410 ms 窗口写进验收口径。成本为零，功能完整。
2. 若一定要消掉窗口，`EmbeddedUI`（调研第 2 点，UIExtension）比并入引擎便宜。
   它不需要搬 JDK，但需要真机确认能否跨应用嵌入。
3. 并入引擎作为长期方案，等 `qflistudio` 真的需要自带 native 能力时再做。

如果选 1，本任务可以就此收口：结果回传、流式、不闪退、退出码都已在 09:10 那轮成立。
