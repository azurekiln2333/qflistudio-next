## 3. 修复项

### 3.1 终结帧后丢失 `dispose` 会永久锁死后台通道（P1）

原 `start()` 用 `current !== null` 判忙。`current` 只在
`disposeSession()` 里清空，而 `disposeSession()` 由 Dart 的 `dispose`
控制触发。若该控制丢失（通道异常、引擎已退），`current` 永远停在已终结
会话上，之后每次后台运行都得到 `busy`，直到重启应用。Dart 侧无法自救：
它已收到终结帧并结束会话。

现在：`current` 已终结（`terminal === true`）时不再报忙，而是退订它的
订阅、丢弃它的暂存帧并清空 `current`，然后继续本次启动
（`StudioBackgroundInterop.ets:272-282`）。未终结的会话仍然报忙，
并发保护不变。

安全性：终结帧只由 `receive()` 在检查通过后标记，所以"已终结"来自接收端
自己的确认，不是本地推断。待淘汰会话的暂存帧属于另一个 `sessionId`，
Dart 的会话过滤会丢弃它们。

### 3.2 事件回调里的未捕获异常（P2，与前台不一致）

`receive()` 直接调用 `sink.success(message)`，前台 `StudioInterop.publishEvent`
对同一处有 `try/catch`。引擎失效时 `success` 抛错会变成事件回调内的未捕获
异常。现在同样包裹并记一行 `sink_failed`（`:249-259`）。这一项是防御性
统一，这里没有可复现的现网异常，也不声称修复了某个已观察缺陷。

| 行 | 含义 |
| --- | --- |
| `QFLI_BACKGROUND launched` | 系统已接受 `startAbility` |
| `QFLI_BACKGROUND start_failed code=<n>` | 启动失败，含业务码 |
| `QFLI_BACKGROUND first_frame kind=<k>` | 跨应用公共事件通道首次送达 |
| `QFLI_BACKGROUND terminal kind=<k> exit=<n> code=<c>` | 收到接收端终结帧 |
| `QFLI_BACKGROUND dispose terminal=<b> launched=<b>` | 会话回收（Dart 放弃或页面销毁） |
| `QFLI_BACKGROUND retire` | 淘汰未回收的已终结会话 |

真机判读方法：有 `launched` 无 `first_frame` ⇒ 跨应用公共事件方向不通，
问题落在传输层，编译器还没跑。有 `first_frame` 无 `terminal` ⇒ 运行中失败、
超时或取消未回传。两者都有而终端没输出 ⇒ 问题在 Dart 或编辑器。

## 4. 修复：两条路线各一个护栏

### 4.1 无窗口接收端优先（C 的 `InteropBackgroundService`，我只补发送端次序）

`startReceiver()`（`StudioBackgroundInterop.ets:343`）的次序改为：
先 `startAppServiceExtensionAbility`（无窗口、不夺前台、Studio 不被冻结），
被拒（801 / 16000004）再退到可见 ability。

判据（下一轮真机）：出现 `QFLI_BG_SERVICE onCreate`，且没有
`QFLI_BG_LIFECYCLE onCreate`；Studio 的 `first_frame` 与 `terminal` 都到。

### 4.2 发送端瞬态额度（本轮新增，属 B）

`reserveSenderAllowance()`（`:114`）在 `startAbility` **之前**申请
`requestSuspendDelay`，`releaseSenderAllowance()`（`:130`）在会话终结或
确认窗口关闭时释放。位置在 `start()` 的 `session.launched = true` 之前（`:454`）。

为什么必须在之前：Studio 拿到额度时还在前台。`startAbility` 之后申请就是
重演 `QFLI_BG_ALLOWANCE attempt=0 ... 9900002`（23:49:30.742 / 23:59:13.819
两次都是 250 ms 后才成功）。

失败不阻断运行：额度被拒只写 `allowance_failed code=<n>`，因为无窗口路线
根本不冻结 Studio。这是"降级但可判读"，不是静默。

新增诊断行（都与既有纪律一致：不含输出文本、令牌、载荷路径）：

## 6. 交给 C 的证据：`BG_START` 之后无输出导致 124
